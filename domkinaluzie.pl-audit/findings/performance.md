# Performance / Core Web Vitals audit — domkinaluzie.pl

## Method

**Measured, live, this session:**
- Real Lighthouse 13.4.1 runs (local Chrome, simulated throttling) against the live URLs — homepage and `/blog/babia-gora-szlaki-porady.html`, mobile (`--preset=perf --form-factor=mobile`) and desktop (`--preset=desktop`) each. This is lab data from an actual Chrome instance hitting production, not an estimate.
- PageSpeed Insights API (`pagespeed_check.py`) was attempted twice and returned `429 PSI rate limit exceeded (240 QPM/25,000 QPD)` both times — no Google API key is configured in this environment (confirmed: `~/.config/claude-seo/google-api.json` does not exist), so PSI/CrUX field data was **not obtainable** this session. This is a tooling limitation, not a site issue — flagging per the "no paid data available" instruction.
- Byte-for-byte transfer figures for the HTML documents, Tailwind CDN, and Swiper were supplied directly by the orchestrating agent from independent `curl` measurements (quoted verbatim below, cross-checked against my own Lighthouse network data where the two overlap — they agree within measurement noise, e.g. Tailwind 126,354 B via curl vs 126,507–126,862 B seen across two separate Lighthouse fetches).
- Source facts (hero markup, `<head>` order, preconnect tags) read directly from `index.html` (6,217 lines) in the repo.

**Not measured (explicitly inferred/flagged as such below):** real-world CrUX field p75 (no API key); INP (Lighthouse is a lab tool and cannot measure INP directly — Total Blocking Time / max-potential-fid are used as the lab proxy, both close to 0 on every run, so no INP red flag is evident in lab conditions, but this is not a substitute for field INP).

## What works

- **TTFB is excellent.** Vercel edge origin responds in 30–33 ms server time on every single Lighthouse run (`server-response-time` audit), and the orchestrator's curl check confirms 103 ms TTFB / 114 ms total for the homepage document with `x-vercel-cache: HIT`. This is not a bottleneck anywhere on the site.
- **Brotli/text compression is active** (`document-latency-insight` → `usesCompression: true`) and the homepage document itself is a lean 44.9 KB compressed despite 234 KB uncompressed source.
- **Desktop and blog performance are genuinely good.** Homepage desktop scores 92/100 (LCP 1.8 s), and the blog post scores 82/100 mobile / **100/100 desktop** (LCP 3.1 s / 0.6 s). The blog post's total payload is 265–266 KB — two orders of magnitude lighter than the homepage.
- **CLS is a non-issue on the homepage** (0.000 on both mobile and desktop) despite the auto-rotating hero slideshow — the slideshow is implemented as opacity-crossfaded, absolutely-positioned `background-image` divs with reserved dimensions, not layout-shifting `<img>` swaps.
- **DOM size is healthy**: 1,184 total elements on the homepage (`dom-size-insight`), well under the 1,500-element red-flag threshold, despite the page being a single ~240 KB file with every section inlined.
- **Google Fonts already use `display=swap` and `preconnect`** (`fonts.googleapis.com` and `fonts.gstatic.com` are preconnected at `index.html:25-26`) — the groundwork for correct font loading is there, it's just not finished (see finding below).

## Findings (ranked by impact ÷ effort)

### 1. Tailwind Play CDN loaded and 100% unused — remove the `<script>` tag
- **Severity:** Critical
- **Evidence:** `index.html:45` — `<script src="https://cdn.tailwindcss.com"></script>`, loaded synchronously in `<head>` with no `defer`/`async`. Orchestrator's direct measurement: 126,354 B compressed transfer, 0 of 167 distinct classes in the served `<body>` match a Tailwind utility pattern. My own Lighthouse run corroborates from the server side: `unused-javascript` audit reports this exact resource as 126,507–126,862 B total, **47,065 B (37%) flagged as literally wasted bytes even by Lighthouse's own static analysis**, and `render-blocking-insight` separately shows it costing **773 ms** of render-blocking time on mobile. `third-parties-insight` also shows 29.3 ms of main-thread time for it. This is on top of the fact that the Play CDN (`cdn.tailwindcss.com`) is a **runtime JIT compiler** — it re-parses and scans the DOM in the browser on every page load looking for Tailwind classes to generate, which it never finds, because the site is hand-written CSS (confirmed: all styling for `.hero-slide`, `.hero-content`, etc. lives in the inline `<style>` block, not Tailwind utilities).
- **Recommendation:** Delete `index.html:44-45` (`<script src="https://cdn.tailwindcss.com"></script>`) and the adjacent `tailwind.config = {...}` block (lines 46+) since it configures a script that's about to be removed. Repeat for every other HTML file that includes it (confirm via `grep -rl "cdn.tailwindcss" .`). **Impact: −126 KB transfer, −773 ms render-blocking time (mobile), removes an in-browser JIT compilation pass entirely, on every single page load, for every visitor.** **Effort: 5 minutes.** This is the single highest impact-per-minute fix on the site.

### 2. Homepage image payload is 5.94 MB across 14 requests — one gallery PNG alone is 2.36 MB
- **Severity:** Critical
- **Evidence:** Lighthouse `resource-summary` (mobile): Image = 14 requests / **5,941,057 B**, out of 6,546,662 B total page weight — images are 91% of the page. The `image-delivery-insight` audit flags **4,185 KiB (≈4.1 MB) of estimated savings**, and names a specific worst offender: a gallery bathroom photo at `https://us-ms.gr-cdn.com/getresponse-IqzZc/photos/5246c6d7-...png`, served as **2,361,221 B (2.36 MB)** for a slot that renders at **316×237 px** (`gallery-grid > .gallery-item > a.gallery-link > img`) — reason given: "Using a modern image format (WebP, AVIF) or increasing the image compression could improve..." This single image is oversized both in *format* (PNG instead of WebP/AVIF) and *dimensions* (full-resolution original serving into a 316×237 box) — wastedBytes on this one file alone is 2,344,559 B, i.e. 99% of it is unnecessary.
- **Recommendation:** Every image served from `us-ms.gr-cdn.com` / `us-wbe-img2.gr-cdn.com` needs to be re-exported at ≤2x display resolution and in WebP/AVIF. If GetResponse's CDN supports on-the-fly resizing/format query params, use them (check their docs); otherwise pre-process and re-upload. Target: no single image over ~150 KB. **Impact: up to ~4.1 MB / 63% of total homepage weight removed — this is the dominant lever for mobile LCP (see Finding 4) and for mobile data cost for visitors on cellular connections, which matters directly for a rural Beskidy tourism audience.** **Effort: 2-4 hours** (re-export + re-upload existing images; no code change needed since `<img>`/`background-image` URLs just get swapped).

### 3. Render-blocking third-party CSS/JS in `<head>` — Swiper, Tailwind, Google Fonts
- **Severity:** High
- **Evidence:** `render-blocking-insight` (homepage, mobile): **3,660 ms estimated savings**, itemized: Swiper JS bundle 1,662 ms, Google Fonts stylesheet 888 ms, Swiper CSS 857 ms, Tailwind CDN 773 ms. Source confirms all four are loaded synchronously with no `defer`/`async`: `index.html:38-42` (Swiper CSS `<link rel="stylesheet">` + Swiper JS `<script src=...>`, both plain, no `defer`), `index.html:27-29` (font stylesheet `<link rel="stylesheet">`, plain), `index.html:45` (Tailwind, plain — see Finding 1, remove entirely rather than defer). Only the GTM `gtag.js` script (`index.html:6`) already carries `async`.
- **Recommendation:** Add `defer` to the Swiper `<script>` tag (`index.html:40-42`) — it only needs to run once the DOM (specifically `.hero-slides`/carousels) exists, not before first paint. Swiper's CSS (`index.html:38-39`) is harder to defer safely without a flash of unstyled carousels, but since the SRI hash is already pinned, consider self-hosting the ~5 KB CSS file inline in the existing `<style>` block (it's tiny) to eliminate that request entirely. Removing Tailwind (Finding 1) removes 773 ms of this by itself. **Impact: with Tailwind already removed, deferring Swiper JS should recover most of the remaining ~2,519 ms (1,662 + 857) of render-blocking time on mobile.** **Effort: 15 minutes** (add one attribute + inline one small CSS file).

### 4. Homepage mobile LCP is 14.0 s (lab, simulated throttling) — element is the H1, gated by the render-blocking chain above
- **Severity:** Critical
- **Evidence:** Lighthouse homepage mobile: `largest-contentful-paint` = **13,979.8 ms** (score 0.56 category overall). `lcp-breakdown-insight` identifies the LCP element as the **H1 headline text** (`body > section#hero > div.hero-content > h1`, "Miejsce dla par, lub grupy przyjaciół...") — not a hero image, because the hero visuals are CSS `background-image` on stacked `<div>`s (`index.html:3328-3339`), which don't register as this page's LCP candidate. The subpart breakdown itself only accounts for TTFB 111 ms + element render delay 3,696 ms (≈3.8 s) — well below the 14 s topline metric. **I cannot fully reconcile this ~10 s gap from the data available in this session** — the most defensible read is that Lighthouse's simulated mobile throttling models bandwidth contention from the 5.94 MB image payload (14 requests, Finding 2) competing with the render-blocking critical-path resources (Finding 3) for the same constrained simulated connection, inflating the observed topline LCP beyond what the isolated subparts suggest. Flagging this explicitly as a **partially inferred causal chain**, not a directly measured one — but note it doesn't change the fix: cutting the image payload and un-blocking the critical path (Findings 1–3) attacks both the confirmed 3.8 s and the unexplained remainder, since both plausible causes point the same direction. Desktop LCP for the same page is a clean 1.8 s (score 92), confirming this is a mobile-network/throttling-sensitive problem, not a server or markup defect.
- **Recommendation:** No separate action beyond Findings 1–3 (kills the render-blocking chain gating the H1) and Finding 2 (kills the bandwidth contention from images). Additionally: since the H1 is the actual LCP element, make sure nothing in the (soon-to-be-trimmed) critical path blocks text paint — text-based LCP should be sub-1s once render-blocking resources are gone, matching the desktop number. **Impact: expect mobile LCP to move from "Poor" (>4.0 s) toward "Good"/"Needs Improvement" band once Findings 1–3 land — verify with a follow-up Lighthouse run after the fix.** **Effort: none additional, covered by Findings 1-3.**

### 5. Four hero slideshow images loaded eagerly from a third-party CDN with no `preconnect`
- **Severity:** Medium
- **Evidence:** `index.html:3327-3340` — all 4 hero slides (`.hero-slide`) are rendered upfront in the DOM with inline `background-image: url('https://us-ms.gr-cdn.com/getresponse-IqzZc/photos/...')`, meaning the browser issues all 4 fetches immediately regardless of which slide is `.active` (only the active slide is visible; the other 3 fetch and decode for nothing until their turn 5–15 s later). `index.html:25-26` shows `preconnect` is set up for `fonts.googleapis.com`/`fonts.gstatic.com` but there is **no `preconnect` or `dns-prefetch` for `us-ms.gr-cdn.com` or `us-wbe-img2.gr-cdn.com`** anywhere in the file (confirmed via grep — only the two font preconnects exist), despite this CDN hosting the actual hero visual and the bulk of the 5.94 MB image weight.
- **Recommendation:** (a) Add `<link rel="preconnect" href="https://us-ms.gr-cdn.com" crossorigin>` (and the `us-wbe-img2` host if it's used above the fold) next to the existing font preconnects — saves a DNS+TLS round trip (Lighthouse measured ~35 ms RTT to this host) on the very request gating the hero's visible background. (b) Lower priority: only fetch the active slide eagerly and load the other 3 lazily/on-idle (e.g. `fetchpriority`/swap the `background-image` in via JS just before rotation) — this doesn't help LCP (images aren't the LCP element per Finding 4) but does reduce the bandwidth-contention effect referenced there. **Impact: ~35-70ms saved on the hero's critical image fetch from preconnect alone; secondary reduction in the image-payload contention discussed in Finding 4.** **Effort: preconnect = 2 minutes; deferred-slide loading = 1-2 hours (small JS change).**

### 6. Blog post CLS 0.15 ("Needs Improvement") — web font swap reflows the article body
- **Severity:** Medium
- **Evidence:** Blog mobile: `cumulative-layout-shift` = **0.150** (numericValue 0.1500670722212666) — crosses the 0.1 "Good" threshold into "Needs Improvement." `cls-culprits-insight` names the shifting element as `body > main.article-wrap` (the entire article body), scored 0.150 — i.e. this single element accounts for the whole page's CLS. `render-blocking-insight` on the same page/run shows the Google Fonts stylesheet costing 885 ms of render-blocking time, which is consistent with a FOUT (flash of unstyled text) reflow: fallback system font paints first, then Playfair Display swaps in with different metrics, reflowing the paragraph text below it. Desktop CLS on the same page is 0.001 (non-issue) — this is a mobile-specific timing problem where the font swap happens later relative to layout.
- **Recommendation:** Add `size-adjust`/fallback-metric-matched `@font-face` overrides for Playfair Display and DM Sans (Chrome and Firefox both support the CSS Font Metric Override properties: `size-adjust`, `ascent-override`, `descent-override`) so the fallback font occupies the same box as the webfont before/after swap — eliminates the reflow without giving up `display=swap`. Alternative/complementary fix: self-host and `<link rel="preload" as="font" ... crossorigin>` the two woff2 files actually used above the fold so they arrive before the layout is committed. **Impact: should bring blog mobile CLS from 0.150 down into the "Good" (≤0.1) band.** **Effort: 1-2 hours** (requires measuring font metrics or using a tool like Fontaine/Capsize to generate the override values).

### 7. Logo images missing explicit `width`/`height`
- **Severity:** Low
- **Evidence:** `unsized-images` audit (homepage) flags `logotyp domki na luzie.png` used at both `nav#navbar > .nav-inner > a.nav-logo > img` and `footer .footer-logo > img` (`index.html`, e.g. `<img src="logotyp domki na luzie.png" alt="Domki na Luzie Logo" style="height: 60px; filter: brightness(1.1);">` — height is set via inline `style`, not the `width`/`height` HTML attributes), plus `logo booking.png`. No measured CLS impact from this currently (homepage CLS = 0.000 on both device types in this run), so this is a latent risk rather than an active bug — but it's a one-line fix per image and removes the risk entirely for slower connections/repaints not exercised in this test run.
- **Recommendation:** Add explicit `width` and `height` attributes (matching the intrinsic aspect ratio) to both logo `<img>` tags; keep the `style="height:60px"` for display sizing, or better, move both to CSS `width`/`height` so the browser can reserve the box before the file downloads. **Impact: negligible in this run's measured conditions but removes a latent CLS risk at effectively zero cost.** **Effort: 10 minutes.**

### 8. Third-party JavaScript weight (GTM) is largely unused on first load
- **Severity:** Low
- **Evidence:** `unused-javascript` audit: `googletagmanager.com/gtag/js` transfers 166,540 B, of which **69,340 B (42%) is flagged unused** by static analysis on this page load. `third-parties-insight` confirms 166,872 B transfer / 38.6 ms main-thread time for GTM — the single most expensive third party on the page by transfer size (ahead of Tailwind and Swiper).
- **Recommendation:** This is largely out of direct control (GTM's bundle size depends on what's configured in the GTM container, e.g. how many tags/triggers are set up), so no code-level fix here — flagging as a **watch item**: if the GTM container has tags that aren't actually needed (old remarketing pixels, unused triggers), trimming them in the GTM UI (not the codebase) would shrink this. Consider also deferring GTM initialization until after first interaction/idle if analytics-on-load accuracy isn't critical for this business. **Impact: up to ~69 KB / ~39ms main-thread if the container is trimmed — unverified without GTM container access.** **Effort: low if done in GTM admin, N/A for code changes.**
